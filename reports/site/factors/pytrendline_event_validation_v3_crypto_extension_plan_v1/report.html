PyTrendline v3 · crypto 180d feasibility benchmark

这页不是 180d alpha 结论页，而是 V3X-C 第一刀 feasibility 子任务：先量清楚当前 visible-line v3 采样器在 180d / 60m 下到底有多重，避免在 30 分钟 cron 里假装能老实跑完整篮子。

Generated: 2026-03-14 03:43 UTC symbols reference: BTC / ETH / SOL / BNB period: 180d interval: 60m window_bars: 96 snapshot_step_bars: 24

先说结论

找到的东西：当前 v3 采样器在 180d/60m 的单币 serial rerun，粗略投影约 43.8 分钟/币；如果按 BTC/ETH/SOL/BNB 四币串行跑，粗略投影约 175.3 分钟。这说明原来的父任务“直接把 crypto 样本扩到 180d”对 30 分钟 cron 来说太大，必须先拆子任务。
没找到的东西：这一步没有产出新的 180d alpha verdict；也没有证明 breakout family 或 rebound watch 在线更长样本里仍然成立。它只回答“这一步多大、该怎么拆”，不回答“哪条信号赢了”。
  • 可靠度：row inventory = high；runtime projection = medium；alpha conclusion = not applicable。
  • 为什么有用：如果先不量成本，后面每轮 cron 都容易卡在“大任务做一半、没法诚实报完成”的尴尬状态。

协议锚点（这轮 benchmark 对应的正式口径）

  • 资产参考：BTC-USD / ETH-USD / SOL-USD / BNB-USD
  • 样本：180d / 60m
  • v3 事件参数：window_bars=96、snapshot_step_bars=24、confirm_bars=2、tol_mult=0.08
  • 观察窗：h6 / h24 / h48 / h72

重点是：这里故意没有偷改协议来“凑快一点”。benchmark 用的就是当前主线想保留的 v3 参数口径，所以投影才有参考价值。

这一步找到了什么 / 没找到什么

  • 找到 1：当前 v3 的 180d crypto 扩样本任务需要先拆，否则单轮 cron 很难诚实闭环。可靠度：high。
  • 找到 2：瓶颈主要在 repeated snapshot line detection + line-by-line candidate scanning，不只是“下载更长数据更慢”。可靠度：medium。
  • 没找到 1：这一步没有给出任何新的 breakout / rebound alpha 方向结论。可靠度：high。
  • 没找到 2：这一步也没有比较 180d 与 45d 的表现差异，因为 full event sample 还没跑出来。可靠度：high。

建议的子任务拆法（给 TODO/cron 用）

  1. C1-a（本轮完成）：冻结 180d crypto 扩样本的 benchmark / 任务拆分基线。
  2. C1-b：先做 BTC-only / 180d / 60m full rerun，并单独出页，不急着混成四币结论。
  3. C1-c：在 BTC 页跑通后，再补 core4（BTC/ETH/SOL/BNB）180d 汇总页。
  4. C1-d：如果 180d core4 页面依然值得继续，再考虑 365d 或做 runtime/checkpoint 改造。
