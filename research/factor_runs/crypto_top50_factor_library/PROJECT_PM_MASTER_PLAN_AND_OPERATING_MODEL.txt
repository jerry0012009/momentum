# 项目 PM 总纲：Factor Library → Signal → Backtest → Cost/Risk → Paper Trading → Transparency

> 角色定位：用户是推动者和把关者；ChatGPT/PM 负责规划、审计、阶段门控和提示词设计；服务器 AI 负责具体执行。
>
> 当前目标：先完成一个可解释、可审计、可复现的 crypto perpetual cross-sectional factor research system / factor library，然后完成 Phase 10、11、12，再做一次完整透明化学习处理。透明化之后，再进入第二轮因子扩展与组合方式扩展。

---

## 1. 项目最终目标

本项目不是单一策略回测项目，也不是为了快速找到一个“神奇因子”。

核心目标是构建一套可持续扩展的量化研究生产线：

```text
数据契约
→ 标签/forward returns
→ 因子工厂
→ factor_values
→ static/dynamic evaluation
→ diagnostic classification
→ redundancy diagnostics
→ curated factor library
→ candidate review
→ multi-factor signal construction
→ diagnostic signal backtest
→ cost/slippage/capacity/risk
→ paper trading
→ transparency closeout
→ 第二轮因子扩展
```

阶段纪律：

1. 新因子默认都是 DIAGNOSTIC_PROBE。
2. CANDIDATE_REVIEW 不是 alpha。
3. diagnostic signal backtest 不是 live trading。
4. 不因为单次 RankIC/Spread 结果直接交易。
5. 不因为单次诊断结果删除因子。
6. 每个 phase 必须有 closeout 和 machine-readable artifacts。
7. PM 审阅通过后才允许进入下一阶段。

## 2. 三方分工

### 2.1 用户

用户的角色不是手动写全部代码，而是：

1. 推动节奏。
2. 把服务器 AI 输出转发给 PM。
3. 接收 PM 审计结论。
4. 将 PM 生成的短提示词或 txt 链接转发给服务器 AI。
5. 学习并掌握关键研究逻辑。
6. 在重大路线选择上做最终判断。

### 2.2 PM / ChatGPT

PM 负责：

1. 定义项目阶段。
2. 审阅服务器 AI commit。
3. 判断 PASS / NEEDS FIX / BLOCKED。
4. 防止服务器 AI 越界。
5. 确保数据、标签、因子、评价、回测口径一致。
6. 把复杂任务拆成服务器 AI 能执行的小任务。
7. 生成适合复制到 Discord 的 txt 提示词。
8. 在关键点向用户解释“为什么这么做”。

PM 不应该把真正的审计外包给服务器 AI。服务器 AI 可以计算、生成表、执行脚本，但 PM 必须判断这些输出是否可信。

### 2.3 服务器 AI

服务器 AI 负责：

1. 读文件。
2. 写代码。
3. 跑脚本。
4. 生成 CSV / parquet / closeout / tests。
5. commit。
6. 返回 changed files、row counts、tests、phase readiness。

服务器 AI 不负责最终判断路线，不负责 alpha claim，不负责自动进入下一阶段。

## 5. Phase 10 后续规划

### Phase 10B-lite：Tail Diagnostics Addendum

目标：补充 tail evidence。

PM 审阅重点：

1. bucket0 是否集中于少数 symbol-date？
2. robust spread 是否仍然为负？
3. 去掉 bucket0 后 spread 是否恢复？
4. 是否需要数据质量审计？
5. 是否需要 signal redesign？
6. 是否需要 horizon-specific direction policy？

可能结论：

```text
A. 需要 bucket0 data audit。
B. 需要 tail-aware signal redesign。
C. 需要 horizon-specific direction policy。
D. 暂停，不进入 Phase 11。
```

### Phase 10C：Signal repair / redesign / audit

Phase 10C 的具体形态取决于 10B-lite 结果。

可能路线：

1. bucket0 data audit：如果极端收益来自少数异常样本。
2. tail-aware signal redesign：如果 bucket0 是真实但非单调结构。
3. horizon-specific direction policy：如果 1h/4h 与 24h/72h 方向不同。
4. robust evaluation redesign：如果 mean spread 被 outlier 污染。

Phase 10C 仍然不应进入交易。

### Phase 10D：Diagnostic signal v1 confirmation

如果 10C 产生 signal v1，需要重新做 diagnostic evaluation：

1. RankIC。
2. robust spread。
3. tail-aware spread。
4. horizon-specific interpretation。
5. quality checks。

只有 signal evaluation 结构稳定，才考虑 Phase 11。

Phase 11 不是优化策略赚钱，而是判断 signal 是否在交易约束下仍值得研究。

Phase 11 应包含：

1. fee model。
2. slippage model。
3. turnover。
4. holding horizon。
5. capacity。
6. liquidity filter。
7. max position / max leverage assumption。


## 11. 用户当前需要理解的最小知识

当前最重要的概念：

### 11.1 RankIC

RankIC 是每个时间点横截面上，signal 排名和未来收益排名之间的相关性。

它看的是整体排序关系。

### 11.2 Quantile spread

Quantile spread 是 top bucket 的平均未来收益减 bottom bucket 的平均未来收益。

它看的是极端头尾。

### 11.3 为什么两者会冲突

如果 signal 在中间区域单调，但在极端低 signal 区域出现强烈反弹，那么：

```text
整体 RankIC 可以为正，
但 top-bottom spread 可以为负。
```

这不是必然 bug，而是信号结构可能非线性。

### 11.4 当前 PM 判断

当前不能简单翻转 signal。
也不能马上进入成本/滑点。
必须先搞清楚 bucket0 是异常值、数据问题，还是稳定结构。
