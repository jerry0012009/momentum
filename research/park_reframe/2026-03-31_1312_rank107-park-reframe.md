## 1) 原 Rank 为什么 park？
原 `Rank 107` 想表达的是：
- 用 `15m / 30m / 60m` 的 `CHOP(14)` 同步计数，
- 当 `charged_count>=2` 时，把它当作 `Fib retest_hold long / EMA continuation long` 的 shared anti-chop veto / size-down 层，
- 不单独开仓，只做 long-side 风险过滤。

原始 source intake 其实把主语说得并不坏：
1. **它不是新 alpha，而是 anti-chop risk layer。**
   - 原 intake 已明确：默认先服务 `Fib retest_hold long` 与 `EMA continuation long`；
   - 也明确说了：若 `breakout-short` 上看不到改善，就不能硬包装成 shared admission gate。
2. **最初的 digest 还给过它一个很窄的正向线索。**
   - `2026-03-20_0008_mtf-chop-chargedup-retest-veto-gate.md` 里，代理快检最强的读法不是 `breakout-short`，而是：
   - `charged_count>=2` 更像 **`Fib retest_hold long` 的 veto**；
   - retest long 的 `charged>=2` 子样本明显更差，fail rate 也更高。
3. **但真正把它压回 park 的 clean replication 很直接。**
   - 严格 queue-facing 口径下，实际剩下的样本几乎只剩 `ema_continuation_long`；
   - `baseline` 约 `-15.42bps`，`hard_veto` 约 `-15.57bps`，`size_down` 约 `-15.41bps`；
   - `hard_veto` 只有一点点 fail-rate 改善（约 `29.41% -> 28.76%`），但 expectancy 没变好；
   - `charged>=2` 占比只有约 `4.57%`，说明这层在严格口径里也很薄。

翻成人话：
**Rank 107 被 park，不是因为 “anti-chop” 完全没信息，而是因为它一旦被写成 `Fib + EMA` 共用的 long-side shared gate，真正通过 clean replication 留下来的只剩 EMA continuation，而在这条线上它并没有给出足够诚实的 candidate 级增量。**

## 2) 它更像 hard park 还是 soft park？
我的判断：**`soft park`，而且比原审计时更偏 soft-to-narrow，而不是 hard。**

为什么不是 hard park：
- 原始 digest 对 `retest_hold long` 给出的方向性证据其实挺清楚；
- clean replication 失败的关键，不是“所有 lane 都证伪”，而是 **真正留下的 queue-facing 样本只剩 EMA continuation long**；
- 也就是说，失败更像“角色写太宽 / lane 混错”，而不是 “CHOP charged-up 完全无信息”。

为什么也不能直接翻案：
- 原始 `shared anti-chop gate` 这版写法已经被 honest 收口为 `park / evidence pool`；
- `EMA continuation long` 这条线上 clean replication 没给它 candidate 资格；
- 因此不能把原 `Rank 107` 重新抬回桌面，只能保留原 `park`，再问是否存在更窄的新主语。
