## 1) 原 Rank 为什么 park？
原始证据来自：
- `research/optimization_loop/2026-03-20_0115_rank104-post-break-signflip-intake.md`
- `research/optimization_loop/2026-03-20_0149_rank104-clean-replication-park.md`
- `research/quant_digests/2026-03-19_2227_post-break-signflip-density-gate.md`

原 Rank 104 的核心写法是：
- 把 breakout 之后短路径里的 `sign-flip density` 当作 post-break hold-quality / management 读数；
- 希望用“前几根走得顺不顺”去帮助决定后续持有或提前退出。

它最后被 park，原因很清楚：
1. digest 级证据一开始就显示：`low_flip` 并不天然更好，甚至更容易在 `8-bar` 维度回吐；
2. clean replication 再把它收紧成 **strict non-leaky early-window** 后，残余价值进一步变薄：
   - `baseline_hold8 mean_net_ret ≈ -7.94bps`
   - `overlay_exit_low_after_3bars mean_net_ret ≈ -7.79bps`
   - 只改善了约 `+0.16bps`
3. 尾部风险也只是轻微削薄：
   - `tail_loss_p05 ≈ -179.13bps -> -167.15bps`
4. side split 更说明问题：
   - `long` 提前退反而略差（`≈ -12.79bps -> -13.08bps`）
   - `short` 虽有一点改善（`≈ -3.55bps -> -2.99bps`），但远不足以支撑升格
5. 也就是说，这条线留下的不是“可独立站住的新 alpha / 新 gate”，而只是一个**很弱的 post-break risk-management 影子**。

翻成人话：
- 原 Rank 104 并没有证明“突破后越顺越值得抱”这件事；
- 更诚实的 early-window 版本只帮你少挨一点点尾部回撤；
- 但它既没把整体收益翻正，也没形成足够干净、足够强的 queue-facing 单轴。

## 2) 它更像 hard park 还是 soft park？
**结论：`soft park`，但偏硬。**

为什么不是 hard park：
- 它不是完全没信息；
- `sign-flip density` 至少碰到了一个真实问题：breakout 之后的路径质量，确实会影响 continuation / failure 的后验读法；
- 轻微削尾也说明它不是纯噪音。

为什么又说“偏硬”：
- 这点信息量太薄，改善量级只有 `0.x bps`；
- 它没有形成可独立 deployment 的 admission / overlay；
- 一旦继续往前救，最自然的方向就会滑向更上位的 `event-driven final-verdict / failure-routing` 语言，而不再像 `Rank 104` 自己。

所以它不是主题彻底死掉，但对 `Rank 104` 这版写法来说，已经接近“只剩很薄残余”的状态。

## 3) 有没有“可救信号”？
**有，但只剩一层很薄的 post-break verdict / 风险管理残余。**

保留下来的信号主要是：
1. 它更像在读 **breakout 后路径质量**，而不是在提供一个新的 entry gate；
2. 真正有用的部分不是“顺滑 continuation 更该奖励”，而是“有些 path quality 读数能稍微帮助你少抱一些坏单”；
3. 这使它留下的残余，更像一种 **failure-verdict / hold-quality note**。

但问题也同样明确：
- 这点残余没有把 expectancy 推过成本门槛；
- 它没有证明自己值得长成新的 queue-facing 派生 rank；
- 而且这层语义已经和现有 `Rank 105`（body-defined honest failure verdict）以及 `Rank 33`（false-reclaim veto / failure-routing hint）高度重叠。

## 4) 最值得改的唯一一刀是什么？
如果只保留 **1 条唯一主修改轴**，本轮最值得保留的一刀会是：

**把 `post-break sign-flip density` 从“可单列 shared overlay / management gate”进一步降级成上位 `event-driven final-verdict` 框架里的一个 path-quality feature，不再尝试把它单独包装成 queue-facing rank。**
